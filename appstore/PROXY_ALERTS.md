# プロキシの異常をメールで受け取る設定

回数制限に当たったときや、AI 側でエラーが出たときに、メールで通知を受け取るための設定です。
対象は2つのプロキシです。

| サービス（Cloud Run） | 使っているもの |
|---|---|
| `gemini-api-key-proxy` | 脈ありAIジャッジ（アプリ） |
| `aiharajudge` | ハラスメント判定サイト |

- 仕組み: プロキシが異常時に `PROXY_ALERT` で始まる1行をログに出します。Google Cloud の「ログベースのアラート」がその行を見つけて、メールを送ります。
- **設定済みです（2026-11-13）。** プロジェクト「Gemini API」（`gen-lang-client-0191915462`）に、アラート「プロキシ異常通知 (PROXY_ALERT)」を作成しました。通知の間隔は1時間、自動クローズは7日です。2つのプロキシは同じプロジェクトにあるので、この1つが両方に効きます。2章は、作り直すときの手順として残しています。
- アラートを作った直後の数分間は、ログが出ても通知されません。テストは作成から3分以上あけて行います。
- メールアドレスは Google Cloud 側にだけ登録します。プログラムにもリポジトリにも書きません（どちらのリポジトリも公開されているため）。

## 1. 通知される内容

ログの行は次の形です。`service` でどちらのプロキシか、`kind` で何が起きたかが分かります。

```
PROXY_ALERT service=myakuari kind=ip_10min_limit limit=20 ip=203.0.113.5
```

| `kind` | 意味 | 緊急度 |
|---|---|---|
| `ip_10min_limit`（脈あり）/ `ip_minute_limit`（ハラスメント） | 1つの IP が短時間の上限を超えた | 低。連打や自動アクセスの可能性 |
| `ip_day_limit` | 1つの IP が24時間の上限を超えた | 中。同じ IP からの大量利用 |
| `global_day_80pct` | 全体の24時間の上限の80%に達した | 中。このままだと全員が使えなくなる |
| `global_day_limit` | 全体の24時間の上限に達した | 高。全員が判定できない状態 |
| `model_unavailable` | Gemini のモデルが提供終了（404）で、予備のモデルに切り替えた | 中。動いてはいるが、設定の更新が必要 |
| `gemini_error` | Gemini がエラーを返した（利用枠の超過、キーの無効など） | 高。判定できていない可能性 |

同じ `kind` の行は、プロキシ側で1分に1行までに抑えています。

## 2. アラートを作る（必須）

1. Google Cloud コンソールを開き、2つのプロキシがあるプロジェクトを選ぶ。
2. 左のメニュー →「ロギング」→「ログ エクスプローラ」を開く。
3. クエリ欄に次を貼り、「クエリを実行」を押す。

   ```
   resource.type="cloud_run_revision"
   textPayload:"PROXY_ALERT"
   ```

4. クエリ欄の下（または「操作」メニュー）にある「アラートを作成」を押す。
5. 次のように入力する。

   | 項目 | 入れる値 |
   |---|---|
   | アラート名 | `プロキシ異常通知` |
   | 含めるログ | 手順3のクエリがそのまま入っていることを確認 |
   | 通知の間隔 | `1 時間`（攻撃が続いても1時間に1通まで） |
   | インシデントの自動クローズ期間 | `1 日` |
   | 通知チャンネル | 下の手順6で作るメール |

6. 通知チャンネルの欄で「通知チャンネルを管理」を開く →「Email」の「新規追加」→ 通知を受け取りたい Gmail アドレスと表示名を入れて保存 → 元の画面に戻り、更新ボタンを押して、そのメールを選ぶ。
7. 「保存」を押す。

画面の日本語表記は、時期によって少し変わることがあります。見つからないときは、「Monitoring」→「アラート」→「ポリシーを作成」ではなく、必ず「ログ エクスプローラ」から作ってください（ログの文字列を条件にできるのはこちらだけです）。

---

## 3. 届くか試す

アラートを作ったあと、わざと上限を超えて通知が来るか確かめられます。Claude Code に「通知のテストをして」と頼めば、こちらで実行します。

自分で試す場合は、ハラスメント判定サイトで判定ボタンを1分以内に11回押します。11回目で「アクセスが集中しています」と表示され、数分以内にメールが届きます。

メールが届いたら、Google Cloud の「Monitoring」→「アラート」に「インシデント」が1件できています。放っておいても1日で自動的に閉じます。

## 4. 通知が来たときの見方

メールの中のリンクからログを開くと、`PROXY_ALERT` の行が見られます。

| 見えたもの | すること |
|---|---|
| `ip_10min_limit` や `ip_minute_limit` が1〜2行だけ | 何もしなくてよい。回数制限が止めています |
| 同じ `ip=` が何度も出る | 何もしなくてよい。しつこい場合は Cloud Run の前段でその IP を遮断することを検討 |
| いろいろな IP で大量に出る、`global_day_80pct` が出る | 攻撃の可能性。Google Cloud の「お支払い」で利用額を確認する。正当な利用が増えただけなら、環境変数 `GLOBAL_DAILY_LIMIT` を上げる |
| `global_day_limit` | 全員が止まっている。正当な利用なら `GLOBAL_DAILY_LIMIT` を上げてデプロイする。攻撃なら、そのまま止めておくのが安全 |
| `model_unavailable` | 環境変数 `GEMINI_MODELS` の先頭を、いま提供されているモデル名に変える |
| `gemini_error status=429` | Gemini API の利用枠を超えている。Google AI Studio で枠と課金設定を確認する |
| `gemini_error status=400` や `403` | API キーが無効になっていないか確認する |

---

## 5. 知っておくこと

- 回数のカウントは、Cloud Run のインスタンスごとに別々です。インスタンスが増えると、実際の上限は設定値より多くなります。通知は「上限に当たった」ことを知らせるもので、正確な回数を数えるものではありません。
- 認証に失敗したリクエスト（合言葉が違うもの）は、回数にも通知にも入りません。
- この通知は利用を止めません。止めるのは回数制限です。課金の通知は、別に「予算アラート」で設定します（`PROXY_TOKEN.md` の7章）。
- ログベースのアラートは、Google Cloud の無料の範囲で使えます。
